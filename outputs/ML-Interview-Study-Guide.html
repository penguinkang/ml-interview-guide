01Sliding Window: Customer Support EventsMedium+

Medium · 준비 우선순위
시간 창·상태 관리의 기본 coding 역량 확인.

Question

You receive events:

(timestamp, customer_id)

Return all customers who generated more than k events within the last 10 minutes.

Approach

customer_id → deque[timestamps]

새 event가 오면:

  1. deque에 timestamp 추가
  2. 10분보다 오래된 timestamp 제거
  3. deque 길이가 k보다 큰지 확인

Complexity

Time: O(n)
Space: O(n)

각 event는 deque에 한 번 들어가고 한 번 빠진다.

Interview follow-up

What if you receive 1 million events per second?

답변은:

  • partition by customer_id
  • distributed stream processing
  • Kafka/Kinesis
  • stateful processors
  • TTL state
  • checkpointing
  • eventual vs exact semantics

까지 확장.

11Fine-tuning vs Prompting vs RAGCritical+

Critical · 준비 우선순위
역할의 핵심인 fine-tuning 투자 판단과 RAG 경계를 설명.

Question

When would you fine-tune instead of using prompting or RAG?

Strong answer

“I separate knowledge problems from behavior problems. If the model lacks fresh or proprietary knowledge, I usually start with retrieval. If the model understands the task but doesn't consistently exhibit the desired behavior or decision boundary, fine-tuning becomes more attractive. Prompting is usually my first option when the task is still evolving because it gives the fastest iteration cycle.”

그리고:

“They're often complementary rather than mutually exclusive.”

Jay connection

Intuit의 production SLM은 frontier LLM call을 대체하면서 약 8× latency reduction과 97%+ reliability를 달성했다.

# Q13 바로가기
14What is the difference between SFT and DPO?High+

High · 준비 우선순위
post-training 및 alignment 기법의 목적 차이를 명확히 설명.

Answer

SFT

Learn:

input → desired response

DPO

Learn preference:

chosen response > rejected response

Strong explanation

“SFT teaches the model what a good answer looks like. Preference optimization teaches the model which of multiple plausible answers better matches our desired behavior.”

# Q14 바로가기
15DPO vs PPO/RLHFCritical+

Critical · 준비 우선순위
RL 도입 판단·복잡도·reward 위험을 포함한 기술 깊이 확인.

Answer

DPO:

  • simpler
  • offline preference pairs
  • stable training
  • no explicit reward model required in basic setup

PPO/RLHF:

  • supports explicit reward optimization
  • potentially more flexible
  • operationally more complex
  • reward hacking/stability concerns

Great Senior Staff line

“I wouldn't introduce RL complexity unless the remaining error distribution actually requires it.”

# Q16 바로가기
17Explain LoRAHigh+

High · 준비 우선순위
fine-tuning의 구현 선택과 학습·serving trade-off 확인.

Answer

Instead of updating full weight matrix:

W' = W + BA

where low-rank matrices B/A are trained.

Benefits:

  • lower GPU memory
  • faster training
  • easier multiple adapters

Follow-up

LoRA vs full fine-tuning?

Answer:

depends on:

  • data volume
  • distribution shift
  • desired capacity
  • infrastructure
  • serving architecture
# Q17 바로가기
18What is quantization?High+

High · 준비 우선순위
optimization 역할에 필요한 정밀도·품질·하드웨어 판단.

Answer

Reduce numerical precision:

FP16/BF16 → INT8 → INT4

Benefits:

  • memory reduction
  • throughput improvement
  • potentially lower latency

Tradeoff:

  • quality degradation
  • kernel/hardware support

Follow-up

Would you quantize every model?

No.

Benchmark task quality and actual serving latency first.
